# トラブルシューティング

問題が起きたら、**まずコマンドラインで再現してください**。エディタ内のエラーは情報が少ないことが多く、
コマンドラインなら具体的な原因が分かります：

```bash
./resampler --log-level debug render <样本> /tmp/t.wav C4 100 "" 0 500 0 0 100 0 '!120' AA
```

## 症状早見表

| 症状 | 考えられる原因 | 対処 |
| --- | --- | --- |
| `info` でモデルが `[缺失]` と表示される | モデルが `models/` に置かれていない | `./download_models.sh` を実行する（Windows: `.\download_models.ps1`）。または `--models` で実際のディレクトリを指定する |
| モデルのダウンロードが遅い/失敗する | GitHub への直接接続が不安定 | スクリプトは自動的に gh-proxy ミラーへ切り替えます。`NR_MODEL_MIRROR=https://gh-proxy.com/` でミラーを強制することもできます |
| ボコーダのバックエンドが `stub` | 同上 | 同上。**Stub は接続確認専用で、音質は実用になりません** |
| F0 のバックエンドが `world-dio` | `fcpe.onnx` がない | 機能的には正常ですが、歌声の場面ではやや不安定です。FCPE を使いたければモデルを追加してください |
| 出力の長さが明らかにおかしい | `length` の単位は**ミリ秒** | 1 秒が欲しければ `1000` を渡します。`44100` ではありません |
| 出力がほとんど無音 | 入力サンプルが小さすぎる / ラウドネス正規化が音を押さえている | 入力の音量を確認する。`output.wave_norm: false` を試して比較する |
| 音がこもる、覆われたように聞こえる | `mel.*` がモデルの仕様と不一致 | デフォルトの `mel.*` に戻す。`mel_scale: slaney` を確認する |
| 音が砕ける、金属音が混じる | `mel_layout` の誤判定 | `vocoder.mel_layout: channels_first` または `frames_first` を明示的に設定して試す |
| ピッチが全体的におかしい | 音名の形式 / F0 モード | 音名が `C4` のような形式か確認する。`f0.mode` を変えて試す（[F0 モード](f0-modes.md) を参照） |
| ビルド時に ort のリンクエラー | GPU 用 feature を複数同時に有効化している | **`--all-features` を使わないでください**。GPU 用 feature は相互排他です |
| プロセス終了時に SIGSEGV（exit 139） | `load-dynamic` リンク時の dylib バージョン不一致 | 下の [load-dynamic のバージョン制約](#load-dynamic-版本约束) を参照 |
| 毎回レンダリングが遅い | キャッシュミス | `cache.enabled: true` を確認する。設定を変更するとフィンガープリントが変わり再構築されます |
| macOS で「開けません」と出る | バイナリが未署名 | `xattr -d com.apple.quarantine ./resampler` |
| UTAU で反応しない | パスに空白や中国語文字が含まれる | プログラムを空白・中国語文字のない純粋な英数字パス（例：`C:\nr\`）に置く |
| ログに pitchBend の警告が出る | pitchBend 文字列の長さが異常 | すでに寛容に処理されており、末尾の文字が落とされるだけで、レンダリング全体には影響しません |

## どの層の問題かを見分ける

この順序で調べると、すばやく絞り込めます：

**1. モデルはあるか？**

```bash
./resampler info
```

2 つとも `[已就绪]` なら揃っています。

**2. エンジンは音を出せるか？**

```bash
./resampler selftest
```

内蔵生成の 440Hz テスト音で一通り実行します。ここで失敗するなら問題はエンジン/モデル側にあり、
あなたの音源とは無関係です。

**3. あなたのサンプルは音を出せるか？**

```bash
./resampler render <你的样本> /tmp/t.wav C4
```

selftest が通ってここで失敗するなら、問題はサンプル自体（形式、サンプルレート、長さ）にあります。

**4. エディタのパラメータは正しいか？**

コマンドラインで鳴るのにエディタで鳴らないなら、問題はエディタ側の呼び出し引数かパス設定にあります。

## ログ

ログレベルを上げると、モデル読み込み、バックエンド選択、Mel の形状、F0 の統計などの詳細が見られます：

```bash
./resampler --log-level debug --models ./models info
```

`--log-format json` は構造化ログを出力し、スクリプトでの処理に便利です：

```bash
./resampler --log-format json render a.wav b.wav C4 2>&1 | grep '"level":"error"'
```

## load-dynamic のバージョン制約

デフォルトの配布成果物は ONNX Runtime をバイナリに**静的リンク**しているため、この問題は起きません。
しかし `load-dynamic` 方式で自分でビルドした場合（実行時に `libonnxruntime.so` /
`onnxruntime.dll` を読み込む）には、分かりにくい落とし穴があります：

**dylib のバージョンは、ort-sys がビルド時に期待するバージョンと正確に一致している必要があります**（例：1.28.0）。
隣接するバージョン（例：1.19.2、1.22.0）では——レンダリングはまったく正常ですが、**プロセスの終了時に
SIGSEGV が発生します**（exit 139）。クラッシュ地点は `exit() → ld-linux 析构 → libonnxruntime` で、
gdb のスタックトレースはライブラリのアンロード問題に見えますが、実際は ABI 非互換によるクリーンアップパスの範囲外アクセスです。

調べ方：

* 読み込まれているライブラリのバージョンを確認：`ldd resampler | grep onnxruntime` のあと、その so のバージョンを調べる
* ビルド設定に対応する正確なバージョンに替えるか、静的リンク（デフォルトの配布モード）へ切り替える
* 終了コードをチェックする CI ホストでは、この問題は「レンダリングは成功したがタスクが失敗」として現れます

## キャッシュ関連

キャッシュファイルは入力と同じディレクトリの `.nrc`（zstd 圧縮）です。キャッシュキー = ソースファイルのパス + サイズ + mtime +
設定フィンガープリント + サンプルレート なので：

* 設定を変更 → 自動で無効化して再構築
* ソースファイルを変更 → 自動で無効化して再構築
* `.nrc` を手動で削除しても、次のレンダリングが 1 回遅くなるだけで、壊れません

キャッシュを無効化するには：`cache.enabled: false`。

## それでも解決しないとき

以下の情報を添えて [Issues](https://github.com/Henley04/neural-resampler/issues) で質問してください：

* `./resampler info` の完全な出力
* 再現に使ったコマンドラインと引数
* `--log-level debug` のログ
* OS とプラットフォーム
